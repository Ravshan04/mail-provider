# Webhook integration

[Documentation index](README.md) · [API reference](api.md)

Webhook subscriptions receive mailbox event notifications generated by background polling. They do not deliver full message contents. The receiver can fetch a message through the scoped HTTP API after handling its event.

## Create a subscription

1. Add the destination's exact hostname to `Mail:WebhookHosts` and restart the application. For environment configuration, the first entry is `Mail__WebhookHosts__0`.
2. Sign in to the workspace and create a subscription through **Webhooks**, or `POST /api/v1/webhooks` in the same authenticated browser.
3. Save the returned `signingSecret` privately; it is returned only on creation.

Example request body:

```json
{
  "mailboxId": "00000000-0000-0000-0000-000000000001",
  "url": "https://receiver.example.com/clarvio-mail"
}
```

The mailbox must belong to the signed-in workspace. Subscription creation and removal require a browser session plus a CSRF token; an API key is insufficient. Each workspace can have up to 20 active subscriptions.

Destinations must use HTTPS on the default port, an allowed hostname, and public network addresses. Redirects and private-address connections are blocked. The allowlist is empty by default; a local HTTP receiver is not an accepted webhook destination.

## Payload and headers

Example payload, with placeholder identifiers:

```json
{
  "eventId": "00000000-0000-0000-0000-000000000002",
  "type": "message.received",
  "mailboxId": "00000000-0000-0000-0000-000000000001",
  "messageId": "provider-message-id",
  "createdAt": "2026-10-05T00:00:00Z"
}
```

The request includes:

```text
Content-Type: application/json
X-Clarvio-Mail-Event: <eventId>
X-Clarvio-Mail-Signature: t=<unix-seconds>,v1=<lowercase-hex-hmac>
```

The signature is HMAC-SHA256 using the signing secret as UTF-8 bytes, over the timestamp string, a literal period, and the raw UTF-8 JSON request body:

```text
HMAC-SHA256(secret, timestamp + "." + raw-request-body)
```

Verify against the exact bytes received before parsing or reserializing JSON. Reject missing/malformed signatures, compare the digest in constant time, and enforce timestamp freshness according to the receiver's clock tolerance. Store `eventId` for deduplication. The timestamp and signature are regenerated for each delivery attempt.

Example Python verification helper; `raw_body` must be the original request bytes:

```python
import hashlib
import hmac
import time


def verify_signature(secret, header, raw_body, tolerance_seconds=300):
    try:
        parts = dict(part.split("=", 1) for part in header.split(","))
        timestamp = parts["t"]
        supplied = parts["v1"]
        if abs(int(time.time()) - int(timestamp)) > tolerance_seconds:
            return False
        expected = hmac.new(
            secret.encode("utf-8"),
            timestamp.encode("ascii") + b"." + raw_body,
            hashlib.sha256,
        ).hexdigest()
        return hmac.compare_digest(expected, supplied)
    except (KeyError, ValueError, TypeError, AttributeError, UnicodeError):
        return False
```

The five-minute tolerance is an example receiver policy, not an enforced service setting. Keep receiver clocks synchronized. A valid signature alone does not prevent duplicate processing.

## Delivery behavior

Delivery is **at least once**. Persist or enqueue a verified event before returning a successful HTTP status. A successful 2xx response marks the delivery complete. A timeout or non-success response causes another attempt, with exponential delays capped at one hour, up to 10 attempts before `dead_letter`.

Inspect deliveries in the workspace or with `GET /api/v1/webhook-deliveries`. Records expose `id`, `eventId`, `subscriptionId`, `status`, `attempts`, `nextAttemptAt`, and `lastStatusCode`. The list returns the latest 100 records. There is currently no API for manually replaying a dead-letter delivery.

Disabling a subscription stops future delivery for that subscription. A repeated request can still reach a receiver after it has already processed an earlier attempt; deduplicate before applying side effects.

## Polling limitations

Only mailboxes with active subscriptions are polled. The initial synchronization is suppressed, so adding a subscription is not a historical mailbox export. The default poll interval is 60 seconds, with a minimum configured value of 15 seconds.

Gmail change history and Microsoft folder delta APIs differ. Events are based on provider change results; validate receipt/update behavior against live mailboxes before treating every event as a newly delivered email. This implementation does not configure native Gmail push or Microsoft Graph webhook subscriptions.
